# 架构决策记录（ADR）

每条记录一次**做过的选择**：背景、决策、被否方案、后果。按时间顺序，Phase 2 起编号。
Phase 1 的决策见 `doc/README.md`（命令模式、快照式 Memento、io 门禁、手写 XML 解析等）。

## ADR-1：扩展点用**接口 + 注册表**，不用继承或事件总线

**背景**：Phase 1 的类型分派写在注册表与渲染器里，要加一个图形类型得改内核。需要找到一个边界，
让第三方代码能在不改内核的前提下添加类型、命令、显示与属性语义。

**决策**：四个扩展点都定义成**纯接口**（`ShapeProvider` / `CommandExtension` / `TreeDecorator` / `AttributeHandler`），
内核只持有"接口 → 实例"的注册表，通过一个 `PluginContext` 暴露注册方法。插件是一次性 `activate(ctx)` 调用的对象。

**被否方案**：

- *基类继承*：插件继承 `CommandBase` 之类。缺点是插件被迫接受内核的实现细节（生命周期顺序、内部字段），
  且 TypeScript 单继承会挡住插件自己的结构，内核改动容易破坏插件。
- *事件总线*：发出 `command:before` 之类事件让插件挂接。缺点是顺序不可控、失败无法回滚、
  "这条命令归谁处理"没有明确答案——而属性处理器恰恰需要"首个命中独占"的确定语义。
- *依赖注入容器*：对 20 条命令的规模属于过度设计，且需要引入运行时依赖（违反零依赖约束）。

**后果**：

- 好：内核只依赖接口，`check-layers.mjs` 可以机械地验证边界；插件测试可以用简单对象构造，不必 mock 内核。
- 好：`box` 的接入对 `src/` 零改动（提交 `c082226` 的 `git show --stat -- src` 为空），这是最有说服力的证据。
- 代价：接口一旦发布就该保持兼容，加字段要用可选属性（本次 `matchesElement` / `derivedIds` / `afterRestore` 都是可选的）。
- 代价：类型分派变成了两次查表（按名 / 按标签），阅读代码时比 `switch` 多跳一次。

## ADR-2：注册用**暂存区 + 原子提交**，不允许"边注册边生效"

**背景**：一个插件会注册多个扩展（`box` 一次注册 1 个类型 + 2 个属性处理器 + 1 个装饰器）。
如果第三个注册撞名，前两个已经生效，运行时就处于"半个 box"的状态：能 `create box` 却 `set label` 报错。

**决策**：`ExtensionRegistry` 提供 `beginRegistration / commitRegistration / discardRegistration`。
`activate` 期间所有注册进暂存区，`commit` 时一次性校验（同类别重名、默认 Provider 的标签冲突）并原子应用；
任一项冲突就抛 `duplicate registration: <category>/<name>`，**一条都不应用**。`activate` 抛错同样丢弃暂存区。

**被否方案**：

- *先注册再回滚*：需要记录"应用了哪些"，回滚代码本身容易写错（例如装饰器已进入渲染链）。
- *启动时不校验，用到才发现*：冲突会变成运行期随机行为，而配置装配恰恰是启动时才加载插件的。

**后果**：

- 好：`activateChecked` 成为唯一加载路径，方式 A/B 共享；测试能断言"冲突后注册表里 box 仍只有一份"。
- 好：错误信息直接指明冲突的类别与名字，用户改配置或改插件名即可。
- 代价：插件内部不能"注册一个然后立刻用这个注册去决定后续注册"——本次三个插件都不需要这种能力；
  若将来需要，应改为两阶段（先声明、后绑定），而不是放松原子性。

## ADR-3：`box` 复用 `<g>` 标签，靠 `data-kind` 区分（标签变体）

**背景**：`box` 由"一个 `<rect>` + 一个 `<text>`"组成，最自然的 SVG 表示是 `<g>`。
但 Phase 1 的 `read` 是"标签名 → 类型"的一对一映射，`<g>` 已经被普通分组占用。

**决策**：给 `ShapeProvider` 加一个可选钩子 `matchesElement(attributes)`，把这类类型称为**标签变体**；
注册表允许"一个默认 Provider + 若干变体"共享标签，`read` 时先试变体、都不中再回落默认。
`box` 序列化成 `<g id="n1" data-kind="box">`，`data-kind` 既是写出的标记也是读回的判据。

**被否方案**：

- *`box` 独占 `<box>` 标签*：写出的 SVG 在浏览器里不渲染，考试要求"生成的 SVG 能被浏览器打开"就不成立了。
- *用 `class="box"`*：`class` 在 SVG 里是样式语义，用户很可能用来做 CSS 主题，冲突时无法区分是插件标记还是用户样式。
- *不共享标签，改用 `<g data-…>` + 类型名存在属性里但 `read` 仍按 `g` 处理*：那就丢掉了"读回来还是 box"的能力，round-trip 不成立。

**后果**：

- 好：保存的文件是合法 SVG，浏览器能直接打开；round-trip 逐字节稳定（有测试）。
- 好：`derivedIds` 让 `<id>-rect` / `<id>-label` 在创建前参与查重；`afterRestore` 让结构不完整的 box 读入失败并保持原文档。
- 代价：`read` 时属性判定要遍历变体列表，标签变体越多判定越贵（当前规模可忽略）。
- 代价：`data-kind` 是一个"插件协议属性"，需要写进用户文档，否则用户手改文件时不知道它的含义。

## ADR-4：属性处理器**首个命中独占**，并由子树快照保证单次 undo

**背景**：`set n1 fill #223344` 对一个 `box` 不是"改 `<g>` 的属性"，而是**改内部底板矩形**的 `fill`
（规范 §3.1 把实际修改写死为 `n1-rect` 的 `fill`）。如果让每条属性都在 `set` 里加分支，
内核就得知道"哪种图形 + 哪个属性 + 落到哪个子部件"；如果让处理器自己管事务，插件就得理解历史栈。

**决策**：`SetAttributeCommand` 先用白名单判断基本属性，未知属性交给
`AttributeHandlerRegistry.findHandler(shape, attr)`，**首个命中独占**；处理器只负责"怎么改"，
事务由命令层的子树快照（Phase 1 的 `ShapeStateRecorder`）提供——处理器抛错就整体回滚，且不进历史。

**被否方案**：

- *多个处理器串联*：语义不明确（谁决定最终值？失败算谁的责任？），且 undo 会变成"部分成功"。
- *处理器返回命令列表*：增加了插件的复杂度，并且仍然需要事务语义，等于把内核的活推给插件。
- *`fill` 走白名单直接设到 `<g>` 上*：`<g>` 上的 `fill` 会被子元素继承，看似可行，
  但读回时"用户改的是框体底色"这一层语义已经丢失，且无法表达"只改底板、不动标签"。

**后果**：

- 好：插件只需要实现"改哪几个字段"，不需要理解历史与回滚；内核的失败回滚对插件自动生效（有测试）。
- 好：`read()` 可选钩子让 undo 能恢复到处理器自己的"旧值"（例如从底板读 `fill`）。
- 代价：处理器顺序即优先级，后注册的同名语义永远不会生效——需要在文档里写清楚，且冲突不报错；
  本次用"类名前缀"约定（`box-*`）避免误伤。

**补充（规范对齐）**：debug 阶段曾让 `fill` 同时改写标签字色（自动配对比色），意图是避免"浅底浅字"。
但规范把 `fill` 的实际修改明确限定为内部矩形的 `fill`，多改一个子部件属于规范之外的副作用，
也会让"标签字色"失去独立可控性。最终实现**只改底板**，字色需要时用 `set <box>-label fill …` 显式指定。
这条取舍说明**处理器的价值不在"批量写同一个值"，而在"把用户级语义翻译成子部件级语义"**——
后者才是白名单做不到、必须由插件拥有的部分。

## ADR-5：两种装配方式共用 `activateChecked`，用**真实进程**证明等价

**背景**：要求"通过修改代码"和"通过修改配置"装配出的行为一致。手工比对不可重复，且容易只看主路径。

**决策**：把"加载插件 + 校验清单"收敛成唯一函数 `activateChecked(extensions, entry)`；
方式 A（`src/main-code.ts`）与方式 B（`src/main.ts --config`）都只负责"把插件对象搞到手"，之后完全同路。
等价性用 `tests/assembly.test.ts` 起**真实 CLI 进程**比对 stdout 字节。

**被否方案**：

- *在测试里直接比两个 `assembleCli` 调用的返回值*：绕过了 REPL 与 `main.ts` 的参数解析，恰好是最容易出岔子的两层。
- *只做人工演示*：无法防止回归，也无法在 CI 里跑。
- *让方式 B 走一条"配置专用"的装配分支*：多一条路径就多一处偏移，等价性会变成"需要维护的巧合"。

**后果**：

- 好：等价性是结构性保证，不是巧合——两条路只差"谁实例化插件"。
- 好：非法配置、缺模块两种失败场景也在这套真实进程测试里覆盖。
- 代价：进程级测试比单元测试慢（每个用例一次 `node` 启动，约 200ms），因此只保留 5 个高价值用例。

## ADR-6：清单加载器放在**内核**，模块加载放在**宿主**

**背景**：方式 B 需要读 JSON、校验结构、按 `entry` 找模块。哪些属于内核，哪些属于 Node 宿主？

**决策**：JSON 的**结构校验与路径解析规则**放内核（`src/core/config/PluginManifestLoader.ts`），
"怎么真正把一个说明符变成模块对象"通过 `PluginModuleLoader` 接口由宿主实现
（`src/host/NodePluginModuleLoader.ts` 用 `createRequire`）。内核不 import `node:path`，自带极简路径工具。

**被否方案**：

- *全放宿主*：内核就无法校验配置，只能信任宿主；换宿主（浏览器演示页）时要重写整套规则。
- *全放内核并直接 import node 模块*：会破坏"内核与运行时无关"与零依赖检查（`check-dependencies.mjs` 会拦下）。

**后果**：

- 好：配置规则（`./` 相对配置目录、绝对路径原样、其余按包名交给 Node 解析）只有一份实现，可被单元测试直接验证。
- 好：宿主适配器里**没有**"插件名 → 路径"的映射表，接入新插件只改配置；模块解析规则属于宿主，清单语义属于内核。
- 代价：内核里有一份 60 行的路径工具，Windows/POSIX 两种分隔符都要自己处理（本次就在这里踩了一次坑，见 §3.1）。
- 代价：`entry` 必须是可 `require` 的 JS，`.ts` 源码要先进编译器——这个边界需要明确写进文档，否则用户会困惑。

## ADR-7：为"零内核改动"**预先**准备通用钩子（提交 3 与 4 分离）

**背景**：`box` 需要共享标签、需要派生 id 查重、需要保护必要子部件。这些能力看起来是为 `box` 定制的；
如果写进 `box` 的提交里，就变成"改内核 + 加插件"的混合提交，"接入插件不需要改内核"的说法就失去了证据。

**决策**：先提交一个**只用通用语言**描述的内核增强（提交 `dd9286c`：标签变体、派生 id、子部件保护），
再提交插件本身（`c082226`）。后者对 `src/` 的差异为 0，可以机械验证。

**被否方案**：

- *一个提交搞定*：省事，但证据消失。
- *在插件里绕开*：例如插件自己维护 id 表，或不管子部件被删——都会留下不一致的隐患。
- *不提供这些能力，降低 box 的要求*：例如 box 独占 `<g>`（回到 ADR-3 的否决项）。

**后果**：

- 好：`git show --stat c082226 -- src` 为空，是最简洁有力的证据。
- 好：三个钩子都是**可选**的，既有 Provider 一行不改；54 个 Phase 1 用例仍然全绿。
- 代价：多做一次提交，且内核里出现了当前只有一个使用者（`box`）的钩子。
  以"接口语言"而非"box 语言"命名与注释（`matchesElement` 而不是 `isBox`）来降低这个代价。

## ADR-8：复合图形的保护契约必须覆盖**四类**改写，而不是"防止子部件离开"

**背景**：`protectsChildren()` 最初只用来挡 `delete` 与 `addto`（"别让必要子部件离开"）。
全面 debug 时发现这个定义**太窄**，至少有三种方式能绕过它把结构搞坏：

1. `create rect x 0 0 5 5 in n1` —— 往 box 里**加**第三个子部件；
2. `front n1-rect` —— 把子部件**重排**，顺序变了；
3. `group gnew n1-rect` —— `group` 内部会把成员从原父级**摘走**，绕过删除保护。

三种都能得到"`save` 成功、`read` 报 `invalid box`"的**自毁文件**——用户自己刚存的文件打不开，
这是最坏的失败形态：错误发生在写入之后，用户已经失去了旧文件。

**决策**：把契约定义为**四向**：容器自报保护后，内核拒绝「删 / 移走 / 加入 / 重排」四类改写。
四处检查都放在 `EditorSession` 的门面方法里（`requireRemovable` / `requireAcceptsChildren` + `reorder` 分支），
因此无论命令来自内置插件还是第三方插件，都走同一道闸门。

**被否方案**：

- *让 `afterRestore` 宽容一点*（缺子部件就自动补上）：会把"文件被外部改坏"和"我们用错了命令"两类
  问题都藏起来，而且自动补出的子部件位置/样式从哪来？
- *在 `box` 插件里自己拦截*：插件只被问"这个属性怎么设"，没有拦截会话级命令的钩子；
  真要加就得给插件更大的权限，等于把不变量从内核挪到插件，风险更大。
- *只在 `save` 前校验一次*：能防住写坏文件，但用户仍会看到一个内部已损坏的文档，
  后续 `tree`/`show` 行为无法解释。

**后果**：

- 好：任何能破坏不变量的人口都被封住，`save` 后的文件保证 `read` 得回来（有回归用例锁定）。
- 好：契约仍然是"一个布尔值"，内核不知道 `box` 是什么；`Group` 不实现它，一行不改。
- 代价：`EditorSession` 里多了两处检查和一个分支（+3 个判断点）；错误文案多了一种
  （`cannot add a child to a composite shape` / `cannot reorder the parts of a composite shape`）。
- 教训：写保护逻辑时要问"结构还能被谁改写"，而不是只问"谁能把东西拿走"。

## ADR-9：**加载期失败继续启动**，只有用法错才退出

**背景**：`--config` 加载失败时，早期实现打印 `error:` 后仍继续启动 REPL；debug 阶段一度改成"失败即退出"，
理由是"带着半套插件继续跑会把错误放大成一连串 `unknown command`"。但 Phase 2 规范 §6 明确要求：
加载器的四类失败必须"输出 `error:` 信息并**继续启动，主程序不得退出**"，配置非法时"以默认内置能力启动"。

**决策**：

1. **继续启动**：模块找不到、没有默认导出、清单声明与实际注册不一致、`activate` 抛错、整份配置非法，
   都打印 `error:` 行后继续进入 REPL；已成功的插件与内置能力照常可用。退出码 0。
2. **错误行做区分**：不是笼统的"装配失败"，而是四类固定文案（`plugin not found: …` 等），
   让"配置写错"与"命令不存在"在输出里一眼可分——这正是原先"失败即退出"想解决的问题，
   现在靠**文案精度**解决，而不是靠中止进程。
3. **只有命令行用法错退出**：`--config` 缺参数 → 退出码 **2**，因为它连"要加载哪份配置"都不成立。
4. `warning:` 与 `error:` 都由 `Repl` 的 `prelude` 在**横幅之后**输出，保持"横幅永远是第一行"的约定。

**被否方案**：

- *失败即退出（debug 阶段的做法）*：与规范直接冲突，且用户拿不到内置能力做降级操作。
- *静默跳过坏插件*：等于隐藏问题；`error:` 行必须在输出里留下痕迹。
- *warning 直接写 stdout*：会跑到横幅前面，破坏"第一行固定"的约定，也让方式 A/B 的输出对齐变复杂。

**后果**：

- 好：符合规范的"坏插件不阻断启动"；错误文案精确，仍能快速定位。
- 好：横幅位置不变，两种装配方式的输出仍逐字节可比。
- 代价：`readConfig` 必须把"读文件失败 / 解析失败 / 结构非法"全部折算成错误行而不是异常，
  `main.ts` 的失败出口因此分成"用法错（2）"与"其余（本就继续）"两路。

## ADR-10：`modified-star` 用"**发生过编辑命令**"语义，祖先标记由装饰器自己算

**背景**：`*` 的 dirty 语义有两种可选定义（规范要求二选一并写进 ADR）：
"内容与上次保存不一致"（`undo` 回到保存点后 `*` 消失）与"发生过编辑命令"（`undo` 不消失）。
另外还要回答两个问题：子图形被改时祖先容器行是否标 `*`；同一行多个标签的拼接顺序。

**决策**：

1. **语义 = 发生过编辑命令**：`undo`/`redo` 不撤销 `*`。理由是它只依赖"编辑信号"，不需要为每个图形
   保存内容快照，装饰器状态量小且判定确定；`save` 成功或 `init`/`read` 替换文档时清空。
2. **祖先传播 = 标**：容器行（`g`、`box`、`svg` 根行）若其子树里有被编辑过的图形，也标 `*`。
   否则"某个卡片被改过"在折叠的树上完全不可见。
3. **拼接顺序 = 注册顺序**：`TreeDecoratorRegistry.suffixFor` 按注册顺序累加字符串。
   生产配置里 `box` 先注册、`tree-star` 后注册，因此同一行是 `(box) *`。
4. **内核只广播信号**：`EditorSession` 在每条修改类命令成功后调用
   `decoratorRegistry.notifyEdited(changedIds)`，`undo`/`redo` 传空数组表示"范围未知"。
   内核不知道 `*` 的含义，也不为某个标签开分支。

**被否方案**：

- *内容比对语义*：需要给每个图形存快照并在渲染时逐行比较，成本高，而且要在渲染路径上做序列化；
  换来的"回到保存点即消失"在本阶段不是必需。
- *在 `onEdited` 里向上遍历 `parent` 链补标记*：那时只有 id、没有 `Shape`；改为渲染时对子树做
  "是否有脏子孙"的判定（`hasDirtyDescendant`），`tree <id>` 打印任意子树时同样正确。
- *内核级"脏标记"字段*：会把一个展示性概念塞进模型层，违背扩展点分层的初衷。

**后果**：

- 好：加标签零内核改动（除"编辑信号广播"这一通用钩子，它不属于任何具体标签）。
- 好：`undo` 行为有明确文档与测试（`plugins/tree-star/tests/treeStar.test.ts`）。
- 代价：`*` 在 `undo` 后仍是"脏"的，用户若想回到干净状态只能 `save`；这与"发生过编辑"的定义一致。
